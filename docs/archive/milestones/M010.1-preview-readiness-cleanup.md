# M010.1 Preview Readiness Cleanup

## Summary

M010.1 removes the noisy normal-flow calls to `GET /api/rooms/{room_id}/split/preview`
before split data is ready. The frontend now gates preview calls from the room summary, shows an
expected not-ready state, and disables creator locking until a valid preview exists.

No OCR, payment, deployment, analytics, auth UI, or M011 work was started.

## Issue Fixed

The M010 smoke test found that item-wise rooms repeatedly called split preview while item claims
were incomplete. The backend correctly rejected those requests with validation errors, but the
frontend generated console/network noise during the normal claim flow.

## Readiness Logic

Readiness is frontend-only and uses `GET /api/rooms/{room_id}/summary`.

- Archived or expired rooms are not preview-ready.
- A room needs at least one participant.
- A room needs at least one item and a positive item total.
- Equal split rooms are ready after those base checks.
- Item-wise rooms are ready only when every active item has exactly its full quantity claimed.
- Settling/settled rooms still evaluate from the same summary data so locked rooms can show preview
  totals when the underlying claims remain complete.

If the frontend considers a room ready but the backend still rejects preview with `400`, `409`,
`422`, or `423`, the UI shows an inline retry state and suppresses repeated preview attempts for
the same summary key.

## UI Behavior

Before:

- The preview card hid backend failures by rendering an empty fallback.
- The browser still emitted repeated preview validation failures.
- The creator Lock button was enabled unless the room was already locked.

After:

- Incomplete item-wise rooms show: `Split preview is not ready yet.` and
  `Finish claiming all items to see totals.`
- The frontend does not call split preview while readiness is false.
- The creator Lock button is disabled until readiness is true and preview data exists.
- The lock helper says: `Complete all claims before locking the split.`
- Participant claims and realtime refetch continue while preview is not ready.
