# M015.1 Flow Architecture, Adjustment Math, Theme Identity & Completion UX Repair

## Status

CONDITIONAL PASS.

Implementation, tests, documentation, and mocked local browser evidence are complete. The remaining
condition is dependency audit risk: `npm audit --json` reports 2 moderate advisories through
Next's bundled PostCSS dependency, and npm's suggested fix path is an unsafe major downgrade.
Real Android/iPhone UPI behavior remains outside local automation.

## Scope

M015.1 is a corrective pass after manual testing found that creator identity, discount math,
manual adjustment flexibility, room flow separation, theme identity, and settled-state completion
still needed repair.

## Delivered Changes

Creator identity:

- Room creation accepts payer metadata and creates the creator participant with the payer name when
  available.
- Room payer-name updates sync the creator participant nickname.
- Room summary serialization falls back from legacy `Creator` nickname to `room.payer_name`.
- Frontend participant chips render person name and creator role as separate elements.

Adjustment math:

- Backend owns adjustment polarity.
- Discount/coupon/offer values subtract even when the frontend sends positive amount payloads.
- Legacy negative discount values are normalized before split calculation.
- Percentage adjustments use integer `rate_basis_points`.
- `packaging_fee`, `tip`, `coupon`, `offer`, and `rounding` are added to the adjustment constraint.
- Calculation policy is documented in `docs/architecture/split-engine.md`.

Creator flow:

- Creator room now renders distinct step views for draft, claiming, locked, settling, and settled
  states.
- The locked view is derived from backend `settling` status before settlement requests exist.
- Settling view focuses on the settlement dashboard.
- Settled view is a completion screen with final totals, participant summary, copy summary, and
  create-another-split action.

Theme identity:

- Dark tokens move from green-dominant to midnight navy, slate, cyan/blue primary, and violet
  accent.
- Green is reserved for success and payer-confirmed semantics.
- QR containers remain light for readability.

Product boundary:

- No wallet, escrow, payment gateway, webhook, payment verification, bank verification, refund, or
  fund custody was added.
- Safe language remains `marked paid`, `payer confirmed`, and `disputed`.
