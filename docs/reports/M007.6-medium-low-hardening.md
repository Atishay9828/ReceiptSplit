# M007.6 Medium/Low Hardening

This document lists the technical debt and medium/low priority hardening tasks addressed and identified during Phase 1 validation.

## Addressed Technical Debt
The following medium/low priority issues have been fully resolved in the current hardening phase.

### M-1: Room Lifecycle States
- **Issue:** Previously, rooms lacked a rigorous state machine, leading to unclear transitions and lack of enforcement.
- **Resolution:** A strict state machine (`draft` -> `active` -> `settling` -> `settled` -> `archived` / `expired`) is now enforced in `RoomService.transition_room()`.
- **Status:** Complete.

### M-4: Mutation Guards
- **Issue:** Room participants, items, and adjustments could be mutated even if a room was in a read-only state like `settling` or `settled`.
- **Resolution:** Status guards have been added to `ItemService` and `AdjustmentService`. The API rejects mutations (HTTP 400 or 403) for rooms in `settling`, `settled`, `archived`, or `expired` states.
- **Status:** Complete.

### M-8: Restrict Client-Settable Statuses
- **Issue:** A client could arbitrarily set a room to `settled` or mix state transitions with standard field updates via the `PATCH /api/rooms/{id}` endpoint.
- **Resolution:** The `update_room` endpoint rejects manual setting of `settled` or `expired` states. Furthermore, status transitions cannot be mixed with regular attribute updates in the same payload.
- **Status:** Complete.

### L-3: Split Engine ValueError
- **Issue:** The `SplitCalculator` raised a generic `ValueError` when detecting an unassigned item-wise split, leading to internal server errors (HTTP 500).
- **Resolution:** Replaced with a specific domain error (`UnclaimedItemsExist`) mapped to HTTP 400 Bad Request.
- **Status:** Complete.

### L-6: Remove Development Utilities
- **Issue:** Test data scripts (`fix_tests.py`, `fix_*.py`) were accidentally committed.
- **Resolution:** Unnecessary development utilities removed.
- **Status:** Complete.

### Participant Color Standardization
- **Issue:** Participant colors allowed arbitrary `#RRGGBB` hex values, leading to visual inconsistencies.
- **Resolution:** Missing colors are assigned by `ParticipantService.join_room()` using `pick_available_color()` and the fixed server `COLOR_PALETTE`. Client-provided colors must already belong to `COLOR_PALETTE`; arbitrary valid hex strings and malformed hex strings are rejected with HTTP 400 via `InvalidColor`.
- **Proof tests:** `tests/api/test_participants.py::test_join_room_no_color_assigns_from_palette`, `tests/api/test_participants.py::test_join_room_valid_color`, `tests/api/test_participants.py::test_join_room_arbitrary_hex_fails`, `tests/api/test_participants.py::test_join_room_invalid_hex_fails`.
- **Status:** Complete.

### User Text Sanitization
- **Issue:** User-supplied display strings could carry HTML/script payloads or null bytes into persisted records if sanitization was missed.
- **Resolution:** API request schemas sanitize text fields before service calls using `strip_html()` from `app.shared.validators`: item names in `ItemCreateRequest` / `ItemUpdateRequest`, adjustment labels in `AdjustmentCreateRequest` / `AdjustmentUpdateRequest`, and participant nicknames in `JoinRoomRequest`. `strip_html()` removes all HTML tags with `bleach`, removes null bytes, and trims whitespace before persistence.
- **Proof tests:** `tests/api/test_items.py::test_add_item_sanitizes_html_and_null_bytes`, `tests/api/test_adjustments.py::test_add_adjustment_sanitizes_html_and_null_bytes`, `tests/api/test_participants.py::test_join_room_nickname_sanitization`.
- **Status:** Complete.
